## User Scenarios & Testing *(mandatory)*

### User Story 1 - เข้าสู่ระบบและเห็นข้อมูลตัวอย่างจากฐานข้อมูล (Priority: P1)

นักพัฒนาสั่งคำสั่งเดียวเพื่อสร้างฐานข้อมูลตาม ER diagram และโหลดข้อมูลตัวอย่างเข้าไป จากนั้น Admin เข้าสู่ระบบ
ด้วยบัญชีที่อยู่ในฐานข้อมูล (รหัสผ่านเก็บแบบ hash) และอยู่ในระบบต่อไปจนกว่าจะออกจากระบบหรือ session หมดอายุ
ข้อมูลที่เห็นต้องมาจากฐานข้อมูล ไม่ใช่จากเบราว์เซอร์

**Why this priority**: ทุกเรื่องที่เหลือในงานนี้ต้องมีฐานข้อมูลที่มีข้อมูลและมีผู้ใช้ที่ยืนยันตัวตนแล้วก่อน
และเป็นสิ่งแรกที่แยกระบบนี้ออกจากต้นแบบที่ใช้ mock

**Independent Test**: ลบฐานข้อมูลเดิม สั่งคำสั่งสร้างและโหลดข้อมูล เปิดแอป เข้าสู่ระบบด้วย `admin@colorado.jp`
แล้วดูว่าเข้าได้ ลองบัญชี `locked@colorado.jp` แล้วถูกปฏิเสธ รีสตาร์ทแอปแล้วข้อมูลยังอยู่ครบ

**Acceptance Scenarios**:

1. **Given** ฐานข้อมูลว่าง, **When** สั่งคำสั่งสร้างและโหลดข้อมูลตัวอย่าง, **Then** มีตารางครบตาม ER diagram,
   มีข้อมูลตัวอย่างครบทุกเส้นทางที่ `src/mock/` เคยครอบคลุม และมีบัญชี Admin สองบัญชีตามเดิม
2. **Given** ฐานข้อมูลที่มีข้อมูลอยู่แล้ว, **When** สั่งคำสั่งเดิมซ้ำ, **Then** ไม่เกิดข้อผิดพลาดและไม่มีข้อมูลซ้ำซ้อน
   (ผลลัพธ์ตามข้อสมมติฐานเรื่องการรันซ้ำ)
3. **Given** บัญชี Admin ที่รหัสผ่านถูกต้องและ `fail_attempts` น้อยกว่า 5, **When** เข้าสู่ระบบ, **Then** เข้าได้,
   `fail_attempts` กลับเป็น 0, บันทึก `last_login` และเปิดหน้า Dashboard
4. **Given** รหัสผ่านผิด, **When** เข้าสู่ระบบ, **Then** แจ้งข้อความตาม UC 1A และ `fail_attempts` เพิ่มหนึ่ง
5. **Given** บัญชีที่ `fail_attempts` ตั้งแต่ 5 ขึ้นไป (`locked@colorado.jp`), **When** เข้าสู่ระบบ, **Then** ถูกปฏิเสธด้วยข้อความตาม UC 1A
   แม้รหัสผ่านถูก
6. **Given** ผู้ใช้ที่ยังไม่ได้เข้าสู่ระบบ, **When** เปิดหน้าใดในระบบโดยตรงด้วย URL, **Then** ถูกพาไปหน้าเข้าสู่ระบบ
7. **Given** Admin เข้าสู่ระบบในเบราว์เซอร์ A แล้วแก้ข้อมูลหนึ่งรายการ, **When** เปิดระบบในเบราว์เซอร์ B ด้วยบัญชีเดียวกัน,
   **Then** เห็นข้อมูลที่แก้แล้วเหมือนกัน

### User Story 2 - ทุกหน้าที่ดูข้อมูลอ่านจากฐานข้อมูล (Priority: P1)

หน้า Dashboard รายการ Order สินค้า สต๊อก ต้นทุน รายการสั่งซื้อเพิ่ม หน้าจัดส่ง ใบปะ และรายงาน ต้องแสดงข้อมูลที่มาจากฐานข้อมูล
โดยหน้าตาและข้อความเหมือนเดิมทุกประการ

**Why this priority**: เป็นขั้นที่ทำให้ Admin เห็นผลของฐานข้อมูลก่อนจะเริ่มแก้ไขข้อมูล และลดความเสี่ยงของการย้ายก่อนแตะ use case ที่เขียนข้อมูล

**Independent Test**: เปิดทุกหน้าที่มีตาราง ตัวเลขสรุป และรายงานพิมพ์ ตรวจว่าตรงกับข้อมูลตัวอย่างที่โหลด
และเปลี่ยนค่าในฐานข้อมูลโดยตรงแล้วโหลดหน้าซ้ำเห็นค่าเปลี่ยน

**Acceptance Scenarios**:

1. **Given** ข้อมูลตัวอย่างที่โหลดแล้ว, **When** เปิด Dashboard, **Then** ตัวเลขสรุปและกราฟตรงกับจำนวน Order ตามสถานะในฐานข้อมูล
2. **Given** ฐานข้อมูลถูกแก้ค่าโดยตรง (ไม่ผ่านหน้าจอ), **When** โหลดหน้า Order ใหม่, **Then** เห็นค่าที่แก้
3. **Given** เปิดรายงานใบปะสินค้าและรายงานต้นทุนต่อหน่วย, **When** พิมพ์หรือดูตัวอย่างก่อนพิมพ์, **Then** เนื้อหาและรูปแบบเหมือนเดิม
4. **Given** ฐานข้อมูลเชื่อมต่อไม่ได้, **When** เปิดหน้าใดๆ, **Then** แสดงข้อความผิดพลาดที่เข้าใจได้และไม่แสดงข้อมูลเก่าจากที่อื่นแทน

### User Story 3 - ทำงานกับ Order ได้ครบและบันทึกลงฐานข้อมูล (Priority: P1)

Admin นำเข้า Order ตรวจสอบ จับคู่ RSL และยกเลิก Order (4A, 2A, 1S, 7A) ได้ครบเหมือนเดิม ทุกการเปลี่ยนแปลงบันทึกลงฐานข้อมูล
และผลของงานอัตโนมัติที่ต่อจากนั้นยังเดินตามเดิม

**Why this priority**: Order คือหัวใจของระบบ และเป็นกลุ่ม use case แรกที่ต้องพิสูจน์ว่า "พฤติกรรมที่อนุมัติแล้วคงเดิม" บนฐานข้อมูล

**Independent Test**: เดินสถานการณ์ที่ 7, 8, 11 และ 12 ใน quickstart ของ feature 001 (นำเข้า ตรวจสอบ ยกเลิก)
แล้วตรวจว่าผลเหมือนเดิมและข้อมูลอยู่ในฐานข้อมูลหลังรีสตาร์ท

**Acceptance Scenarios**:

1. **Given** กล่องรับ Order จาก Rakuten (mock) มีรายการใหม่, **When** Admin กดนำเข้า (4A), **Then** Order ที่ครบถ้วนถูกสร้างที่ "รอตรวจสอบคำสั่งซื้อ",
   SKU ที่ไม่ลงทะเบียนไป "รอดำเนินการด้วยตนเอง", ข้อมูลไม่ครบไม่ถูกนำเข้า และรายการที่ซ้ำถูกข้าม ตามเดิม
2. **Given** Order ที่รอตรวจสอบ, **When** Admin ยืนยัน (2A), **Then** 2S และ 3S ทำงานต่อและ Order ไปสถานะที่ถูกต้องตามจำนวนสต๊อก
3. **Given** Order ที่ยกเลิกได้, **When** Admin ยกเลิก (7A), **Then** สถานะ เหตุผล และการคืนสต๊อกบันทึกครบ; Order ที่ส่งมอบแล้วเป็น "รอดำเนินการพิเศษ" ตามเดิม
4. **Given** การนำเข้ากดซ้ำพร้อมกันสองครั้ง, **When** ทั้งสองคำสั่งทำงาน, **Then** ไม่เกิด Order ซ้ำสำหรับ marketplace_order_id เดียวกัน

### User Story 4 - สินค้า สต๊อก ต้นทุน และการสั่งซื้อเพิ่มบันทึกลงฐานข้อมูล (Priority: P2)

Admin จัดการข้อมูลสินค้าและกฎ SKU ดูและปรับสต๊อก ดูต้นทุนต่อหน่วย และตัดสินใจสั่งซื้อเพิ่มจาก Supplier
(3A, 3S, 4S, 5A, 6A) โดยข้อมูลทั้งหมดอยู่ในฐานข้อมูล

**Why this priority**: จำเป็นต่อวงจรเต็ม แต่ Order flow (Story 3) ใช้ได้ก่อนถ้าข้อมูลสินค้าถูกอ่านจากฐานข้อมูลแล้ว

**Independent Test**: เดินสถานการณ์ใน use case 3A, 4S, 5A, 6A บนข้อมูลตัวอย่าง แล้วตรวจว่าค่าที่แก้คงอยู่หลังรีสตาร์ท
และการลบสินค้าที่ยังมี Order ค้างถูกบล็อกตามเดิม

**Acceptance Scenarios**:

1. **Given** สินค้าใหม่, **When** Admin ลงทะเบียน, **Then** มีแถวสินค้าและแถวสต๊อกคู่กัน และ 2S จับคู่กฎ SKU ได้
2. **Given** ข้อมูลต้นทุนครบ, **When** Admin บันทึกต้นทุน (4S), **Then** คำนวณต้นทุนต่อหน่วยและเก็บประวัติตามเดิม
3. **Given** Order ที่สต๊อกไม่พอ, **When** Admin สั่งซื้อเพิ่ม (5A, 6A), **Then** สร้างรายการสั่งซื้อ ผูกกับ Order และส่งไปยัง Supplier (mock) ตามเดิม
4. **Given** ความล้มเหลวของการบันทึก, **When** use case ทำงานไม่สำเร็จกลางทาง, **Then** ไม่มีข้อมูลที่เขียนไปครึ่งเดียว

### User Story 5 - จัดส่ง ใบปะ แจ้งเลขติดตาม และลบข้อมูลเก่าบันทึกลงฐานข้อมูล (Priority: P2)

Admin ส่งมอบพัสดุให้ขนส่ง พิมพ์ใบปะ แจ้งเลขติดตามให้ลูกค้า ดึงสถานะขนส่ง และลบข้อมูลเก่า (8A, 9A, 5S, 10A)
โดยกฎที่อนุมัติใน feature 001 ยังเป็นจริงทุกข้อ

**Why this priority**: เป็นปลายทางของ flow และครอบคลุมกฎสถานะที่ทีมอนุมัติ (ตัดสต๊อกหนึ่งครั้ง "จัดส่งสำเร็จ" เมื่อขนส่งยืนยันเท่านั้น)

**Independent Test**: เดินสถานการณ์ 1 ถึง 6, 9, 10 และ 13 ของ quickstart feature 001

**Acceptance Scenarios**:

1. **Given** Order ที่พิมพ์ใบปะแล้ว, **When** Admin ส่งมอบและแจ้งเลขติดตาม, **Then** สถานะเป็น "แจ้งเลขติดตามแล้ว" ตัดสต๊อกหนึ่งครั้ง ไม่เป็น "จัดส่งสำเร็จ"
2. **Given** ขนส่ง (mock) ตอบว่าส่งถึงแล้ว, **When** ดึงสถานะ, **Then** Order เป็น "จัดส่งสำเร็จ" และสถานะนี้ไม่ถอยกลับ
3. **Given** ขนส่งตอบว่าตีกลับ, **When** ดึงสถานะ, **Then** Order เป็น "ตีกลับ/คืนสินค้า" และคืนสต๊อกหนึ่งครั้ง
4. **Given** Admin ลบข้อมูลที่ปิดแล้วและเก่ากว่ากำหนด (10A), **When** ยืนยัน, **Then** ลบเฉพาะ Order ที่ "จัดส่งสำเร็จ" หรือ "ยกเลิกแล้ว" พร้อมข้อมูลที่เกี่ยวข้อง และบันทึกประวัติการลบ

### User Story 6 - งานอัตโนมัติทำงานฝั่งเซิร์ฟเวอร์ในธุรกรรมเดียวกับการกระทำ (Priority: P2)

หลังการกระทำของ Admin ทุกครั้ง งาน System (Auto) 2S, 3S, 6S และ 7S ทำงานต่อโดยอัตโนมัติ ผลสุดท้ายของการกระทำและผลของงานอัตโนมัติ
ต้องสำเร็จหรือล้มเหลวพร้อมกัน และการตัดสต๊อกต้องไม่เกิดซ้ำแม้มีคำสั่งหลายอันพร้อมกัน

**Why this priority**: เป็นสิ่งที่ฐานข้อมูลจริงเพิ่มขึ้นมาเทียบกับ mock ในเบราว์เซอร์ (หลายผู้ใช้/แท็บ ความล้มเหลวกลางทาง)
และเป็นข้อกำหนดของหลักการ I ใน constitution

**Independent Test**: เปิดสองแท็บ กดแจ้งเลขติดตามของ Order เดียวกันพร้อมกัน ตรวจว่าสต๊อกลดครั้งเดียว
และจำลองความล้มเหลวของฐานข้อมูลกลางงาน แล้วตรวจว่าไม่มีข้อมูลเปลี่ยนครึ่งเดียว

**Acceptance Scenarios**:

1. **Given** Order เดียวกันถูกสั่งแจ้งเลขติดตามพร้อมกันจากสองแท็บ, **When** ทั้งสองทำงาน, **Then** สต๊อกลดลงตามจำนวนใน Order เพียงครั้งเดียว
2. **Given** การกระทำที่ทำให้งานอัตโนมัติหลายขั้นเดินต่อ, **When** ขั้นหนึ่งล้มเหลว, **Then** ทั้งการกระทำและขั้นที่ทำไปแล้วถูกยกเลิก ข้อมูลกลับเป็นก่อนหน้า
3. **Given** สต๊อกที่เหลือพอสำหรับ Order เดียว, **When** สอง Order ที่ต้องการสต๊อกนั้นถูกตัดพร้อมกัน, **Then** Order หนึ่งสำเร็จ อีกหนึ่งไป "รอดำเนินการด้วยตนเอง" และสต๊อกไม่ติดลบ

### User Story 7 - ระบบภายนอกเป็น mock ผ่าน interface ที่สลับได้ (Priority: P3)

การเรียก Rakuten RMS, RSL, ขนส่ง และการส่งคำสั่งซื้อ Supplier ผ่าน interface ที่ use case รู้จัก
adapter ที่ใช้งานเลือกด้วยค่าตั้งระบบ ตอนนี้มีเฉพาะ mock และ toggle ที่หน้า `/dev` สั่งให้ mock ล้มเหลวได้เหมือนเดิม

**Why this priority**: ไม่เปลี่ยนสิ่งที่ผู้ใช้เห็นวันนี้ แต่ทำให้เพิ่ม Rakuten จริงได้ภายหลังโดยไม่แก้ use case ตามที่ constitution กำหนด

**Independent Test**: เปิด toggle ทุกตัวที่หน้า `/dev` ทีละตัวแล้วเดินทางเลือกของ UC ที่เกี่ยวข้อง ผลต้องเหมือนใน feature 001
และสลับ adapter ผ่านค่าตั้งระบบโดยไม่แก้ use case หรือหน้าจอ

**Acceptance Scenarios**:

1. **Given** toggle "เชื่อมต่อ Rakuten RMS ไม่ได้" เปิด, **When** กดนำเข้า, **Then** แจ้งเตือนและบันทึก log ตาม 4A ทางเลือก #1
2. **Given** toggle ของขนส่งหรือระบบอื่นเปิด, **When** เดินทางเลือกที่เกี่ยวข้อง, **Then** ได้ผลตามทางเลือกของ UC นั้นเหมือนเดิม
3. **Given** adapter ใหม่ที่ทำตาม interface เดียวกัน, **When** เปลี่ยนค่าตั้งระบบให้ใช้ adapter นั้น, **Then** use case และหน้าจอทำงานได้โดยไม่ต้องแก้โค้ดของทั้งสองส่วน
4. **Given** การตั้งค่าปกติ, **When** ใช้งานระบบ, **Then** ไม่มีการเชื่อมต่อออกไปยังระบบภายนอกจริงใดๆ

---

### Edge Cases

- ฐานข้อมูลเชื่อมต่อไม่ได้ขณะเปิดหน้า: แสดงข้อผิดพลาดที่ชัดเจน ห้ามแสดงข้อมูลสำรองจากที่อื่นเงียบๆ
- Session หมดอายุระหว่างทำงาน: พากลับหน้าเข้าสู่ระบบโดยไม่เสียข้อมูลที่บันทึกไปแล้ว
- Admin สองคนแก้ Order เดียวกันพร้อมกัน: การเขียนอย่างหนึ่งต้องไม่ทับอีกอย่างเงียบๆ จนข้อมูลเสีย
- รันคำสั่งสร้างและโหลดข้อมูลบนฐานข้อมูลที่ Admin ใช้งานอยู่: ต้องไม่ลบข้อมูลที่ใช้งานโดยไม่แจ้ง
- โหลดข้อมูลตัวอย่างล้มเหลวกลางทาง: ไม่เหลือฐานข้อมูลที่โหลดครึ่งเดียว
- รหัสผ่านที่เก็บต้องไม่ถูกส่งออกไปที่เบราว์เซอร์หรือปรากฏใน log
- Order ที่มี marketplace_order_id เดียวกันนำเข้าซ้ำ: ข้ามเพียงรายการนั้น
- สต๊อกต้องไม่ติดลบจากการตัดสต๊อกหรือคืนสต๊อกพร้อมกัน
- ข้อมูลที่ฝั่งหน้าจอเคยเก็บเพียงใน mock (เช่น log ข้อผิดพลาดอัตโนมัติ ประวัติการลบ ประวัติต้นทุน log การแจ้งเลขติดตามซ้ำ) ต้องมีที่เก็บในฐานข้อมูล (ดู FR-017)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: ระบบ MUST เก็บข้อมูลทางธุรกิจทั้งหมด (Admin, Order, รายการสินค้าใน Order, สินค้า, สต๊อก, ต้นทุน, Supplier, รายการสั่งซื้อเพิ่ม, ใบปะ) ในฐานข้อมูลจริง และข้อมูลต้องอยู่ครบหลังรีสตาร์ทระบบ
- **FR-002**: ข้อมูลที่ Admin คนหนึ่งบันทึก MUST ปรากฏให้เบราว์เซอร์หรืออุปกรณ์อื่นเห็นเมื่อโหลดหน้าใหม่
- **FR-003**: ระบบ MUST มีคำสั่งเดียวที่สร้างโครงสร้างฐานข้อมูลตามชื่อตารางและคอลัมน์ใน ER diagram และโหลดข้อมูลตัวอย่างที่ครอบคลุมทุกเส้นทางของ use case เท่ากับที่ `src/mock/` ครอบคลุมวันนี้
- **FR-004**: คำสั่งในข้อ FR-003 MUST รันซ้ำได้โดยไม่เกิดข้อผิดพลาดและไม่ทำให้ข้อมูลตัวอย่างซ้ำซ้อน และ MUST NOT ลบข้อมูลโดยไม่แจ้งเมื่อรันกับฐานข้อมูลที่มีข้อมูลอยู่
- **FR-005**: บัญชี Admin MUST เก็บรหัสผ่านแบบ hash เท่านั้น บัญชี Admin แรกและบัญชีทดสอบ `locked@colorado.jp` MUST ถูกสร้างโดยการโหลดข้อมูลตัวอย่าง
- **FR-006**: การเข้าสู่ระบบ (1A) MUST คงพฤติกรรมเดิมทุกข้อ (ตรวจรูปแบบอีเมล, นับ `fail_attempts`, ล็อกเมื่อตั้งแต่ 5, บันทึก `last_login`) และสร้าง session ที่ใช้ต่อได้จนออกจากระบบหรือหมดอายุ
- **FR-007**: ทุกหน้าในระบบหลังเข้าสู่ระบบ MUST ตรวจ session ที่ฝั่งเซิร์ฟเวอร์ ผู้ที่ไม่มี session MUST ถูกพาไปหน้าเข้าสู่ระบบ
- **FR-008**: ทุกหน้าที่แสดงข้อมูล (Dashboard, Order, สินค้า, สต๊อก, ต้นทุน, สั่งซื้อเพิ่ม, จัดส่ง, ใบปะ, รายงาน) MUST อ่านข้อมูลจากฐานข้อมูล และคงรูปแบบ ข้อความ และคำสถานะเดิม (22 สถานะที่ทีมอนุมัติ)
- **FR-009**: use case ทุกตัวของ Admin (1A ถึง 10A) และ System (1S ถึง 7S) MUST คงพฤติกรรม ลำดับขั้น ทางเลือก และข้อความที่อนุมัติแล้วใน feature 001 และใน use case description โดยไม่มี use case ใหม่
- **FR-010**: การเขียนข้อมูลทุกครั้งจากหนึ่ง use case MUST อยู่ในธุรกรรมเดียวที่สำเร็จทั้งหมดหรือไม่เกิดผลเลย และงาน System (Auto) ที่ตามมา MUST อยู่ในธุรกรรมเดียวกับการกระทำที่เป็นต้นเหตุ
- **FR-011**: การตัดสต๊อก (7S) และการคืนสต๊อก MUST เกิดครั้งเดียวต่อ Order แม้มีคำสั่งซ้ำหรือพร้อมกันจากหลายแท็บ และ MUST NOT ทำให้สต๊อกติดลบ
- **FR-012**: SQL ทุกคำสั่งในระบบ MUST เป็น SQL ดิบแบบ parameterized ใช้ชื่อตารางและคอลัมน์ตาม ER diagram และมี Q-number ตามแบบ `Q<UC id>.<n>` ที่ระบุ use case เจ้าของ เพื่อทำตารางรายการ SQL ส่งรายงานได้ครบทุกคำสั่ง (Q-number ยังเป็นค่าชั่วคราวจนกว่าทีมส่งเอกสารฉบับแก้ไข)
- **FR-013**: การเรียกระบบภายนอก (Rakuten RMS, RSL, ขนส่ง, ส่งคำสั่งซื้อ Supplier) MUST ผ่าน interface และมี mock adapter เป็นตัวที่ใช้งานจริง เลือกด้วยค่าตั้งระบบ โดย use case และหน้าจอ MUST NOT รู้จัก adapter ตัวใดโดยเฉพาะ
- **FR-014**: ระบบ MUST NOT เชื่อมต่อออกไปยังระบบภายนอกจริงใดๆ ในงานนี้
- **FR-015**: หน้า `/dev` MUST ยังมี toggle จำลองข้อผิดพลาดของระบบภายนอกทุกตัวและผลของทางเลือกแต่ละ UC ต้องเหมือนเดิม และ MUST มีวิธีรีเซ็ตข้อมูลตัวอย่างกลับเป็นสถานะเริ่มต้น
- **FR-016**: ข้อมูลทางธุรกิจ MUST NOT ถูกเก็บใน `localStorage` ของเบราว์เซอร์ เมื่องานนี้เสร็จ (การเก็บค่ากำหนดการแสดงผล เช่น ภาษา หรือสถานะแถบข้าง ทำได้)
- **FR-017**: ข้อมูลที่หน้าจอใช้อยู่แต่ยังไม่มีในตารางของ ER diagram ได้แก่ log ข้อผิดพลาดอัตโนมัติ ประวัติการลบ 10A ประวัติต้นทุน 4S และ log การแจ้งเลขติดตามซ้ำ 5S MUST มีที่เก็บในฐานข้อมูล ทีมพัฒนาเพิ่มตารางหรือคอลัมน์ส่วนนี้เองเพื่อเดินงานต่อ (ทีมตัดสินใจแล้ว: ตัวเลือก A) และ MUST บันทึกรายการที่เพิ่มไว้ในเอกสารวางแผนเพื่อส่งให้ทีมเอกสารปรับ ER diagram และการออกแบบฐานข้อมูลให้ตรงตามภายหลัง
- **FR-018**: ข้อความผิดพลาดเมื่อฐานข้อมูลเชื่อมต่อไม่ได้ MUST เข้าใจได้และ MUST NOT เปิดเผยรหัสผ่าน ค่าเชื่อมต่อ หรือข้อมูลภายในของระบบแก่ผู้ใช้

### Key Entities *(include if feature involves data)*

- **Admin**: ผู้ใช้เพียงบทบาทเดียวของระบบ มีอีเมล รหัสผ่านแบบ hash จำนวนครั้งที่เข้าสู่ระบบผิด และเวลาเข้าสู่ระบบล่าสุด (ตาราง `admins`)
- **Session**: การยืนยันตัวตนของ Admin หนึ่งครั้ง มีอายุจำกัดและสิ้นสุดได้เมื่อออกจากระบบ
- **Order และรายการสินค้าใน Order**: คำสั่งซื้อจาก Rakuten มีสถานะหนึ่งใน 22 ค่า ข้อมูลจัดส่ง เลขติดตาม และสถานะการตัดสต๊อก แยกส่วนหัว (`orders`) กับรายการสินค้า (`order_items`)
- **สินค้า (SKU) และกฎ SKU**: สินค้าที่จับคู่กับรหัสสินค้าของช่องทางขาย (`skus`) ใช้ในการจับคู่ของ 2S
- **สต๊อก**: ยอดคงเหลือในคลังบริษัทและที่ RSL ต่อสินค้า (`stock`)
- **ต้นทุน**: ส่วนประกอบต้นทุนและต้นทุนต่อหน่วย (`costs`)
- **Supplier และรายการสั่งซื้อเพิ่ม**: ผู้จัดหาสินค้าและคำสั่งซื้อเติมสต๊อก (`suppliers`, `reorders`)
- **ใบปะสินค้า**: ใบปะต่อพัสดุหนึ่งชิ้นของ Order (`labels`)
- **ระบบภายนอก (Rakuten RMS, RSL, ขนส่ง, Supplier)**: ฝั่งที่ระบบเรียกผ่าน interface ซึ่งในงานนี้ตอบด้วย mock

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ทั้ง 13 สถานการณ์ใน `specs/001-order-status-alignment/quickstart.md` ให้ผลเหมือนเดิมทุกข้อเมื่อรันบนระบบที่ใช้ฐานข้อมูล
- **SC-002**: หลังรีสตาร์ทระบบ ข้อมูลทุกรายการที่บันทึกไว้ก่อนหน้าอยู่ครบ 100% และเบราว์เซอร์อื่นเห็นข้อมูลชุดเดียวกันเมื่อโหลดหน้าใหม่
- **SC-003**: นักพัฒนาที่มีเครื่องใหม่ตั้งฐานข้อมูลและเปิดระบบพร้อมข้อมูลตัวอย่างได้ภายใน 10 นาทีโดยใช้คำสั่งสร้างและโหลดข้อมูลหนึ่งคำสั่ง และรันซ้ำอีก 3 ครั้งแล้วจำนวนข้อมูลตัวอย่างไม่เปลี่ยน
- **SC-004**: ในการทดลองตัดสต๊อก Order เดียวกันพร้อมกันจากสองแท็บ 20 ครั้ง สต๊อกลดลงตามจำนวนใน Order เพียงครั้งเดียวทุกครั้ง (20 จาก 20)
- **SC-005**: เมื่อจำลองความล้มเหลวกลางงาน ไม่พบข้อมูลที่เปลี่ยนครึ่งเดียวในการทดลองทุกครั้ง
- **SC-006**: ไม่พบข้อมูลทางธุรกิจใน `localStorage` ของเบราว์เซอร์หลังใช้งานครบทุกหน้า
- **SC-007**: ตารางรายการ SQL ของระบบมีทุกคำสั่งพร้อม UC id และ Q-number ครบ 100% (ไม่มีคำสั่ง SQL ที่ไม่มีเจ้าของ use case)
- **SC-008**: การเปลี่ยน adapter ของระบบภายนอกหนึ่งตัวเป็นตัวอื่นที่ทำตาม interface เดียวกันทำได้โดยไม่ต้องแก้ไฟล์ use case หรือหน้าจอ
- **SC-009**: ผู้ที่ไม่ได้เข้าสู่ระบบเปิดหน้าใดในระบบด้วย URL โดยตรงถูกพาไปหน้าเข้าสู่ระบบ 100% ของหน้า
- **SC-010**: ไม่พบรหัสผ่านแบบข้อความธรรมดาในฐานข้อมูล ใน log หรือในข้อมูลที่ส่งไปยังเบราว์เซอร์

## Assumptions

- ฐานข้อมูลเป็น PostgreSQL ตามข้อกำหนดโครงการใน constitution และใช้เฉพาะ SQL ดิบ ไม่ใช้ ORM
- การรัน "คำสั่งสร้างและโหลดข้อมูล" บนฐานข้อมูลที่มีอยู่แล้วมีสองโหมด: โหมดเริ่มต้นสร้างเฉพาะสิ่งที่ยังไม่มีโดยไม่แตะข้อมูลเดิม และโหมดรีเซ็ตที่ล้างแล้วโหลดใหม่ ซึ่งต้องสั่งอย่างชัดเจน
- ฐานข้อมูลสำหรับพัฒนาตั้งบนเครื่องผู้พัฒนา (เช่น container) และค่าเชื่อมต่ออยู่ในไฟล์ค่าตั้งที่ไม่ถูก commit
- รหัสผ่านทดสอบเดิม (`demo1234`) ใช้ในข้อมูลตัวอย่างเท่านั้น และถูกเก็บแบบ hash ในฐานข้อมูล
- Session ใช้คุกกี้ อายุ session เริ่มต้น 8 ชั่วโมง (ปรับได้ด้วยค่าตั้ง)
- Q-number ยังเป็นค่าชั่วคราวตาม constitution และเปลี่ยนชื่อภายหลังได้เมื่อเอกสารฉบับแก้ไขมา
- ตารางหรือคอลัมน์ที่เพิ่มนอก ER diagram (FR-017) ใช้ชื่อตามแบบของ ER diagram เดิม และทีมเอกสารจะปรับ ER diagram ให้ตรงตามภายหลัง ถ้าฉบับที่ปรับขัดกับที่ทำไว้ ให้ปรับโค้ดตามเอกสารและแก้ด้วย migration ใหม่
- ความแตกต่างระหว่างรูปแบบข้อมูลเดิมในหน้าจอกับ ER diagram (เช่น แยก `order_items` และ `labels`) เป็นเรื่องภายใน ผู้ใช้ต้องเห็นพฤติกรรมเดิม
- หน้า `/dev` ใช้ในสภาพแวดล้อมพัฒนาและสาธิตเท่านั้น
- ผู้ใช้เป็น Admin คนเดียวบทบาทเดียว ไม่มีหน้าจอสำหรับลูกค้า ไม่เกี่ยวกับ Yahoo! Auctions หรือ Amazon
- ไม่ครอบคลุม: การเชื่อมต่อ Rakuten RMS จริง และระบบภายนอกจริงอื่นๆ ทั้งหมด การสำรองข้อมูล การเพิ่มบทบาทผู้ใช้ และ use case ใหม่
