## User Scenarios & Testing *(mandatory)*

### User Story 1 - ตัดสต๊อกแล้ว Order ยังไม่ถือว่าส่งสำเร็จ (Priority: P1)

หลังระบบแจ้งเลขติดตามให้ลูกค้า (5S) ระบบตัดสต๊อก (7S) ให้เองโดยอัตโนมัติ Order ต้องยังอยู่ที่สถานะ
"แจ้งเลขติดตามแล้ว" เพราะพัสดุยังอยู่ระหว่างทาง ระบบแค่จดว่าตัดสต๊อกแล้วและสถานะการซิงค์ยอดไปยัง Rakuten
Admin จึงแยกออกว่า Order ไหนยังรอขนส่งอยู่ และ Order ไหนถึงมือลูกค้าแล้ว

**Why this priority**: ทีมอนุมัติแล้วว่า "จัดส่งสำเร็จ" ต้องหมายถึงถึงมือลูกค้าจริง ถ้า 7S ยังตั้งสถานะนี้
ตัวเลขและสถานะทุกหน้าจะบอกว่าส่งสำเร็จทั้งที่ยังไม่ได้ส่งถึง และ Order จะถูกมองเป็นสถานะสิ้นสุดเร็วเกินไป

**Independent Test**: นำเข้า Order แล้วเดิน flow ตั้งแต่ตรวจสอบ จับคู่ พิมพ์ใบปะ ส่งมอบ แจ้งเลขติดตาม
ดูว่า Order หยุดที่ "แจ้งเลขติดตามแล้ว" พร้อมสต๊อกถูกหักครบจำนวนหนึ่งครั้ง และไม่เป็น "จัดส่งสำเร็จ"

**Acceptance Scenarios**:

1. **Given** Order สถานะ "แจ้งเลขติดตามแล้ว" ที่ยังไม่ได้ตัดสต๊อกและสต๊อกในแหล่งจัดส่งพอ,
   **When** ระบบทำงาน 7S, **Then** ยอดสต๊อกของแหล่งจัดส่งลดลงตามจำนวนใน Order, Order ถูกบันทึกว่าตัดสต๊อกแล้ว,
   แสดงข้อความ "ตัดสต๊อกและอัพเดทจำนวนสินค้าสำเร็จ" และสถานะยังเป็น "แจ้งเลขติดตามแล้ว"
2. **Given** Order ที่ตัดสต๊อกแล้ว (สถานะยังเป็น "แจ้งเลขติดตามแล้ว"), **When** ระบบทำงานรอบถัดไป,
   **Then** ระบบไม่ตัดสต๊อกซ้ำ และสถานะไม่เปลี่ยน
3. **Given** Order สถานะ "แจ้งเลขติดตามแล้ว" ที่ยอดสต๊อกในแหล่งจัดส่งน้อยกว่าจำนวนสั่ง,
   **When** ระบบทำงาน 7S, **Then** ไม่ตัดสต๊อก, แจ้งเตือนว่ายอดสต๊อกไม่เพียงพอ และ Order เป็น "รอดำเนินการด้วยตนเอง" (เหมือนเดิม)
4. **Given** Order ที่ตัดสต๊อกแล้วแต่ซิงค์ยอดคงเหลือไป Rakuten ไม่สำเร็จ, **When** ระบบทำงาน 7S,
   **Then** สต๊อกในระบบถูกตัดไว้ก่อน, สถานะการซิงค์เป็น "รอซิงค์", ระบบลองซิงค์ใหม่เองรอบถัดไป และสถานะ Order ยังเป็น "แจ้งเลขติดตามแล้ว"

### User Story 2 - "จัดส่งสำเร็จ" เมื่อขนส่งยืนยันว่าถึงลูกค้า (Priority: P1)

เมื่อระบบดึงสถานะจากผู้ให้บริการขนส่ง (8A) แล้วพบว่าพัสดุถึงมือลูกค้า Order จึงเปลี่ยนเป็น "จัดส่งสำเร็จ"
ไม่มี use case อื่นตั้งสถานะนี้

**Why this priority**: เป็นอีกครึ่งหนึ่งของการแก้ใน Story 1 ถ้าไม่มีทางเข้าสู่ "จัดส่งสำเร็จ" ที่ถูกต้อง
Order จะค้างที่ "แจ้งเลขติดตามแล้ว" ตลอดไปและไม่ถึงสถานะสิ้นสุด

**Independent Test**: ให้ Order ที่ส่งมอบแล้วและตัดสต๊อกแล้ว กดดึงสถานะจากขนส่งในหน้าจัดส่งเมื่อขนส่งตอบว่า
ส่งถึงแล้ว ดูว่า Order เปลี่ยนเป็น "จัดส่งสำเร็จ" และไม่มีทางอื่นที่ทำให้ Order เป็นสถานะนี้

**Acceptance Scenarios**:

1. **Given** Order สถานะ "แจ้งเลขติดตามแล้ว" ที่ตัดสต๊อกแล้ว, **When** ขนส่งยืนยันว่าส่งถึงลูกค้า,
   **Then** Order เปลี่ยนเป็น "จัดส่งสำเร็จ" และสต๊อกไม่เปลี่ยนจากเดิม
2. **Given** Order สถานะ "อยู่ระหว่างจัดส่ง" หรือ "แจ้งเลขติดตามแล้ว" ที่ขนส่งยังตอบว่าอยู่ระหว่างทาง,
   **When** ดึงสถานะจากขนส่ง, **Then** Order คงสถานะเดิม และหน้าจัดส่งแสดงสถานะจากขนส่งว่าอยู่ระหว่างทาง
3. **Given** การเชื่อมต่อระบบติดตามของขนส่งล้มเหลว, **When** ดึงสถานะ, **Then** แจ้งเตือน "ไม่สามารถดึงสถานะจากผู้ให้บริการขนส่งได้ กรุณาลองใหม่ภายหลัง" และคงสถานะล่าสุดไว้
4. **Given** Order สถานะ "จัดส่งสำเร็จ" อยู่แล้ว, **When** ขนส่งยืนยันส่งถึงซ้ำ, **Then** ไม่มีอะไรเปลี่ยน

### User Story 3 - ยกเลิก ลบข้อมูลเก่า และแจ้งเลขติดตามซ้ำ ยังทำงานถูกต้อง (Priority: P2)

เพราะ Order ที่ตัดสต๊อกแล้วอยู่ที่ "แจ้งเลขติดตามแล้ว" นานขึ้น use case ที่อ้างสถานะนี้ต้องยังถูกต้อง

**Why this priority**: เป็นผลข้างเคียงของ Story 1 และ 2 ถ้าไม่ปรับ Admin จะแจ้งเลขติดตามซ้ำไม่ได้
หรือยกเลิกผิดวิธี

**Independent Test**: เลือก Order สถานะ "แจ้งเลขติดตามแล้ว" ที่ตัดสต๊อกแล้ว ลองกดแจ้งเลขติดตามซ้ำ, ลองยกเลิก,
และเปิดหน้าลบข้อมูลเก่า

**Acceptance Scenarios**:

1. **Given** Order สถานะ "แจ้งเลขติดตามแล้ว", **When** Admin กดส่งเลขติดตามซ้ำและยืนยัน,
   **Then** ระบบส่งซ้ำและบันทึก Log การส่งซ้ำ (5S ทางเลือก #3) โดยสถานะไม่เปลี่ยน
2. **Given** Order สถานะ "แจ้งเลขติดตามแล้ว", **When** Admin กดยกเลิก Order, **Then** ระบบถือว่าพัสดุส่งมอบให้ขนส่งแล้ว
   แจ้งว่าไม่สามารถยกเลิกในระบบได้ทันที และบันทึกคำขอเป็น "รอดำเนินการพิเศษ" (7A ทางเลือก #1)
3. **Given** Order สถานะ "จัดส่งสำเร็จ" หรือ "ยกเลิกแล้ว", **When** Admin กดยกเลิก Order, **Then** แจ้งว่ายกเลิกไม่ได้ (เหมือนเดิม)
4. **Given** มี Order สถานะ "แจ้งเลขติดตามแล้ว" ที่ยังรอขนส่งยืนยัน, **When** Admin เปิดหน้าลบข้อมูลเก่า,
   **Then** Order นั้นไม่ถูกนับเป็นข้อมูลที่ลบได้ มีเฉพาะ "จัดส่งสำเร็จ" และ "ยกเลิกแล้ว" เท่านั้น

### User Story 4 - 3S แยกเส้นทางตามสต๊อกตรงกับ BizFlow และใช้สถานะครบ 22 ค่า (Priority: P2)

3S ส่ง Order ที่สต๊อกพอเข้า 1S และที่สต๊อกไม่พอเข้า 4S/5A ตาม BizFlow To-Be และทุกสถานะที่ระบบตั้งต้องอยู่ใน 22 ค่าที่ทีมอนุมัติ

**Why this priority**: พฤติกรรมนี้ระบบทำอยู่แล้ว Story นี้ล็อกไว้เป็นข้อกำหนดและให้ตรวจซ้ำ
ว่าการแก้ใน Story 1 และ 2 ไม่ทำให้พังหรือเกิดสถานะนอกรายการ

**Independent Test**: นำเข้า Order ที่สต๊อกพอและ Order ที่สต๊อกไม่พอ ดูสถานะปลายทางของแต่ละ Order
และไล่ดูทุกหน้าว่าไม่มีสถานะที่อยู่นอกรายการ

**Acceptance Scenarios**:

1. **Given** Order สถานะ "รอตรวจสอบสต๊อก" ที่ยอดรวมสต๊อก (คลังบริษัท + RSL) พอ, **When** 3S ทำงาน,
   **Then** Order เป็น "ยังไม่ได้จับคู่" เพื่อเข้า 1S
2. **Given** Order สถานะ "รอตรวจสอบสต๊อก" ที่ยอดรวมสต๊อกไม่พอ, **When** 3S ทำงาน,
   **Then** Order เป็น "รอ Admin ตัดสินใจสั่งซื้อ" เพื่อเข้า 4S/5A
3. **Given** Order ผ่านทุกขั้นตอนตั้งแต่นำเข้าจนส่งถึงลูกค้า, **When** ดูสถานะที่ Order เคยมี,
   **Then** ทุกสถานะอยู่ใน 22 ค่าที่อนุมัติ

---

### User Story 5 - ข้อมูลตั้งต้นและปุ่มรีเซ็ตให้ทดสอบทุกเส้นทางได้ (Priority: P3)

หลังรีเซ็ตข้อมูล Admin เห็น Order ตัวอย่างที่อยู่ในแต่ละสถานะของช่วงส่งมอบ และเดินครบทั้งเส้นทาง
ส่งถึง, ส่งไม่สำเร็จ, ตีกลับ, ยกเลิกระหว่างทางได้โดยไม่ต้องแก้ข้อมูลเอง

**Why this priority**: ใช้ทดสอบและ capture รูปลงรายงาน (ตามเกณฑ์ข้อ 33) ไม่กระทบการใช้งานจริงโดยตรง

**Independent Test**: กดรีเซ็ตข้อมูล แล้วลองดึงสถานะขนส่งในหน้าจัดส่ง ดูว่าเห็นผลครบทุกเส้นทาง

**Acceptance Scenarios**:

1. **Given** รีเซ็ตข้อมูลตัวอย่างแล้ว, **When** เปิดหน้าจัดส่ง, **Then** เห็น Order ที่รอขนส่งยืนยัน (ตัดสต๊อกแล้ว),
   Order ที่ส่งถึงแล้ว, Order ที่ส่งไม่สำเร็จ และ Order ที่ถูกตีกลับหลังตัดสต๊อกอย่างน้อยอย่างละหนึ่ง
2. **Given** รีเซ็ตข้อมูลตัวอย่างแล้ว, **When** ดึงสถานะจากขนส่ง, **Then** Order ตัวอย่างอย่างน้อยหนึ่งรายการเปลี่ยนเป็น "จัดส่งสำเร็จ" ผ่านทางส่งถึงลูกค้า
3. **Given** ข้อมูลตั้งต้นทั้งหมด, **When** ตรวจทุก Order, **Then** ไม่มี Order ใดเป็น "จัดส่งสำเร็จ" โดยที่ขนส่งยังไม่ยืนยันส่งถึง

---

### Edge Cases

- ขนส่งยืนยันส่งถึงก่อนที่ 5S แจ้งเลขติดตามหรือ 7S ตัดสต๊อกจะเสร็จ: ระบบบันทึกว่าขนส่งยืนยันแล้ว
  แต่ยังไม่เปลี่ยนเป็น "จัดส่งสำเร็จ" จนกว่า 5S และ 7S จะเสร็จ จึงเปลี่ยนให้เอง (ดู Assumptions)
- ขนส่งตอบ "อยู่ระหว่างทาง" ทั้งที่เคยยืนยันส่งถึงแล้ว (หรือไม่พบเลขติดตามในระบบขนส่ง): คงสถานะส่งถึงไว้ ไม่ย้อนกลับ
- ตีกลับหรือคืนสินค้าหลังตัดสต๊อก ไม่ว่า Order จะยังไม่ถึงลูกค้าหรือถึงแล้ว: Order เป็น "ตีกลับ/คืนสินค้า" และคืนสต๊อกตามจำนวน (เหมือนเดิม)
- พัสดุส่งไม่สำเร็จ: Order เป็น "จัดส่งไม่สำเร็จ" และแจ้ง Admin (เหมือนเดิม)
- ซิงค์ยอดคงเหลือไป Rakuten ไม่สำเร็จขณะที่ขนส่งยืนยันส่งถึงแล้ว: Order เป็น "จัดส่งสำเร็จ" ได้ โดยสถานะ "รอซิงค์" ยังอยู่และระบบลองใหม่
- Admin กดดึงสถานะขนส่งหลายครั้งติดกัน: ผลลัพธ์เหมือนกดครั้งเดียว ไม่ตัดสต๊อกหรือเปลี่ยนสถานะซ้ำ
- Order ที่ค้างที่ "แจ้งเลขติดตามแล้ว" เป็นเวลานานเพราะขนส่งไม่ตอบ: ไม่ถูกลบโดย 10A และยังยกเลิกได้ผ่านเส้นทาง "รอดำเนินการพิเศษ"

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001** (7S): เมื่อตัดสต๊อก ระบบ MUST หักยอดสต๊อกของแหล่งจัดส่งตามจำนวนใน Order บันทึกว่า Order ตัดสต๊อกแล้ว และบันทึกสถานะการซิงค์ยอดคงเหลือไป Rakuten โดย MUST NOT เปลี่ยนสถานะของ Order ออกจาก "แจ้งเลขติดตามแล้ว"
- **FR-002** (7S): ระบบ MUST NOT ตัดสต๊อกซ้ำให้ Order เดียวกัน
- **FR-003** (7S): เส้นทางล้มเหลวของ 7S MUST ทำงานเหมือนเดิม: ยอดไม่พอไม่ตัดสต๊อกและเป็น "รอดำเนินการด้วยตนเอง"; ซิงค์ไม่สำเร็จคงยอดที่ตัดไว้ สถานะซิงค์เป็น "รอซิงค์" และลองใหม่เอง
- **FR-004** (8A): สถานะ "จัดส่งสำเร็จ" MUST ถูกตั้งเฉพาะเมื่อผู้ให้บริการขนส่งยืนยันว่าพัสดุถึงมือลูกค้า ไม่มี use case อื่นตั้งสถานะนี้
- **FR-005** (8A): ถ้าขนส่งยืนยันส่งถึงก่อนที่ 5S และ 7S จะเสร็จ ระบบ MUST บันทึกการยืนยันไว้ และเปลี่ยนเป็น "จัดส่งสำเร็จ" ให้เองเมื่อ 5S และ 7S เสร็จ
- **FR-006** (8A): เส้นทางส่งไม่สำเร็จ ตีกลับ/คืนสินค้า และเชื่อมต่อขนส่งไม่ได้ MUST ทำงานเหมือนเดิม รวมถึงการคืนสต๊อกเมื่อตัดไปแล้ว
- **FR-007** (3S): Order ที่ยอดรวมสต๊อกพอ MUST ไป "ยังไม่ได้จับคู่" และที่ไม่พอ MUST ไป "รอ Admin ตัดสินใจสั่งซื้อ"
- **FR-008**: สถานะ Order ที่ระบบตั้งทุกจุด MUST เป็นหนึ่งใน 22 ค่าที่ทีมอนุมัติเท่านั้น
- **FR-009** (7A): Order สถานะ "แจ้งเลขติดตามแล้ว" MUST ถูกปฏิบัติเหมือนส่งมอบให้ขนส่งแล้ว (ยกเลิกในระบบทันทีไม่ได้ บันทึกคำขอเป็น "รอดำเนินการพิเศษ") ส่วน "จัดส่งสำเร็จ" และ "ยกเลิกแล้ว" MUST ยกเลิกไม่ได้
- **FR-010** (10A): สถานะสิ้นสุดที่ลบได้ MUST มีเฉพาะ "จัดส่งสำเร็จ" และ "ยกเลิกแล้ว"
- **FR-011** (5S): Admin MUST ส่งเลขติดตามซ้ำได้เมื่อ Order อยู่ที่ "แจ้งเลขติดตามแล้ว" โดยไม่เปลี่ยนสถานะและบันทึก Log การส่งซ้ำ
- **FR-012**: หน้าจัดส่ง MUST แสดงสถานะ Order สถานะจากขนส่ง และสถานะตัดสต๊อก/ซิงค์ให้แยกกันชัดเจน
- **FR-013**: ข้อมูลตั้งต้นและปุ่มรีเซ็ตเดิมที่หน้า /dev MUST ทำให้เดินครบทุกเส้นทางของ FR-001 ถึง FR-011 ได้หลังรีเซ็ต โดยไม่ต้องแก้ข้อมูลเอง และไม่มี Order ตั้งต้นที่เป็น "จัดส่งสำเร็จ" โดยขนส่งยังไม่ยืนยันส่งถึง (หน้า /dev ไม่ต้องเพิ่มปุ่มหรือตัวเลือกใหม่)
- **FR-014**: ขอบเขตเฉพาะช่องทางขาย Rakuten Ichiba
- **FR-015** (8A): เมื่อขนส่งยืนยันส่งถึงแล้ว สถานะจากขนส่งของ Order MUST NOT ย้อนกลับเป็น "อยู่ระหว่างทาง" เอง รวมถึง Order ที่เป็น "จัดส่งสำเร็จ" อยู่แล้ว ยกเว้นเมื่อขนส่งแจ้งว่าตีกลับหรือคืนสินค้า

### Key Entities

- **Order**: สถานะ Order (หนึ่งใน 22 ค่า), สถานะจากขนส่ง (อยู่ระหว่างทาง, ส่งถึงแล้ว, ส่งไม่สำเร็จ, ตีกลับ), ข้อมูลว่าตัดสต๊อกแล้วหรือยัง, สถานะการซิงค์ยอดคงเหลือไป Rakuten, ข้อมูลว่าแจ้งเลขติดตามแล้วหรือยัง
- **สต๊อก**: ยอดคลังบริษัทและยอด RSL ต่อ SKU ที่ 7S หักและที่การตีกลับคืนให้
- **ข้อมูลติดตามพัสดุจากขนส่ง**: สถานะการจัดส่งล่าสุดต่อเลขติดตาม ใช้เป็นหลักฐานเดียวที่ทำให้ Order เป็น "จัดส่งสำเร็จ"

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Order ที่เป็น "จัดส่งสำเร็จ" 100% มีการยืนยันส่งถึงจากขนส่ง ทั้งหลังรีเซ็ตข้อมูลและหลังเดินทุกเส้นทาง
- **SC-002**: เมื่อเดิน Order หนึ่งรายการจากนำเข้าจนแจ้งเลขติดตาม Order หยุดที่ "แจ้งเลขติดตามแล้ว" พร้อมสต๊อกถูกหักเท่าจำนวนสั่งพอดีหนึ่งครั้ง
- **SC-003**: ไม่พบสถานะที่อยู่นอก 22 ค่าที่อนุมัติในหน้าจอใดเลย
- **SC-004**: Admin เดินครบสี่เส้นทาง (ส่งถึง, ส่งไม่สำเร็จ, ตีกลับหลังตัดสต๊อก, ยกเลิกระหว่างทาง) จากข้อมูลที่เพิ่งรีเซ็ตได้ภายใน 10 นาที โดยใช้เฉพาะหน้าจอของระบบ
- **SC-005**: กฎเดิมของ 7A และ 10A ไม่ถอยหลัง: Order ที่ปิดแล้วยกเลิกไม่ได้ และมีเฉพาะ Order ที่ปิดแล้วเท่านั้นที่ลบได้ 100% ของกรณีทดสอบ

## Assumptions

- ทีมอนุมัติรายการสถานะ 22 ค่าและข้อ (1) ถึง (3) แล้วเมื่อ 2026-10-10 และ 2026-10-12; เอกสาร use case ฉบับปัจจุบันยังไม่แก้ตาม ทีมจะแก้เอกสารภายหลัง เมื่อได้ฉบับใหม่ต้องตรวจ spec นี้ซ้ำ
- 3S ในเอกสาร use case ฉบับปัจจุบันเป็นหน้าดูสต๊อกของ Admin ไม่ได้อธิบายการแยกเส้นทางของ Order การแยกเส้นทางใน spec นี้อ้างอิง BizFlow To-Be และสิ่งที่ระบบทำอยู่แล้ว
- เมื่อขนส่งยืนยันส่งถึงก่อน 5S และ 7S จะเสร็จ ใช้ค่าตั้งต้นว่ารอให้ทั้งสองเสร็จก่อนแล้วจึงเป็น "จัดส่งสำเร็จ" เพื่อไม่ให้ข้ามขั้นตอนที่ทำงานจากสถานะ "แจ้งเลขติดตามแล้ว"
- การตีกลับ/คืนสินค้าหลังส่งถึงลูกค้าแล้ว ยังเกิดได้และคงพฤติกรรมเดิม (เปลี่ยนเป็น "ตีกลับ/คืนสินค้า" และคืนสต๊อก)
- ระบบยังใช้ข้อมูลตัวอย่างในเบราว์เซอร์ ไม่เชื่อมฐานข้อมูล จึงไม่ครอบคลุมเรื่อง SQL, Q-number หรือโครงสร้างตาราง
- ข้อความแจ้งเตือนและชื่อสถานะทั้งภาษาไทยและอังกฤษใช้ตามที่มีอยู่ ไม่เพิ่มข้อความใหม่นอกจาก use case รองรับ
- นอกขอบเขต: การรับสินค้าจาก Supplier แล้วกลับเข้า 3S, การรับคืนสินค้าเข้าสต๊อกเป็น use case ใหม่, ช่องทางขายอื่นนอกจาก Rakuten
