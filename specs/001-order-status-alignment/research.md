# Research: จัดลำดับสถานะ Order ให้ตรงตามที่ทีมอนุมัติ

ไม่มี NEEDS CLARIFICATION เหลือใน Technical Context ข้อด้านล่างคือการตัดสินใจเชิงออกแบบที่ต้องเลือกก่อนเขียน tasks
อ้างอิงโค้ดปัจจุบัน: `src/lib/workflow.ts` (`runAutomation` ช่วง 7S, `pollCarrier`, `notifyTracking`, `checkCancel`, `planClosedCleanup`),
`src/mock/delivery.ts`, `src/mock/orders.ts`, `src/app/(app)/shipping/`

## 1. จุดที่เลื่อนสถานะเป็น "จัดส่งสำเร็จ"

- **Decision**: เพิ่มกฎใน `runAutomation` ที่เลื่อน Order จาก "แจ้งเลขติดตามแล้ว" เป็น "จัดส่งสำเร็จ" เมื่อ
  `stock_deducted` เป็นจริง และ `delivery_status` เป็น `delivered`
- **Rationale**: `pollCarrier` บันทึก `delivery_status` ที่ขนส่งตอบอยู่แล้ว (ทางแยก `else` ที่เรียก `patchOrder`)
  การเลื่อนสถานะจึงเป็นงานอัตโนมัติแบบเดียวกับ 2S/3S/6S/7S ที่ทำงานต่อทันทีหลังทุก action
  กฎเดียวนี้ครอบคลุมทั้งกรณีขนส่งยืนยันหลัง 7S และกรณียืนยันก่อน 5S/7S เสร็จ (FR-005) โดยไม่ต้องมีสถานะพิเศษ
  และไม่มี use case อื่นตั้ง "จัดส่งสำเร็จ" (FR-004)
- **Alternatives considered**:
  - ให้ `pollCarrier` ตั้งสถานะเองตรงๆ: ไม่ครอบคลุมกรณียืนยันก่อน 7S เสร็จ และทำให้ 5S/7S ถูกข้าม เพราะ 7S ทำงานจากสถานะ "แจ้งเลขติดตามแล้ว" เท่านั้น
  - เพิ่มสถานะใหม่ เช่น "รอขนส่งยืนยัน": ผิดข้อกำหนดที่ล็อก 22 ค่า

## 2. รูปแบบกฎ 7S ใหม่

- **Decision**: ใน `runAutomation` เมื่อ Order เป็น "แจ้งเลขติดตามแล้ว": ถ้ายังไม่ตัดสต๊อก ให้ตัดตามแหล่งจัดส่งแล้วบันทึก `stock_deducted: true`
  และ `mp_stock_synced` โดยไม่เรียก `setStatus`; ถ้าตัดแล้ว ให้ข้ามไปเช็คกฎเลื่อนสถานะและกฎซิงค์ซ้ำ (ไม่ `continue` ทิ้ง)
  ต้องอ่าน Order ล่าสุดจาก state ไม่ใช้ตัวแปรวนรอบเก่า
- **Rationale**: เดิมสาขา "ตัดแล้ว" จบด้วย `setStatus` แล้ว `continue` ทำให้กฎ "ลองซิงค์ Marketplace ใหม่" (7S ทางเลือก #1)
  ไปรันกับ Order ที่ออกจากสถานะนี้แล้วเท่านั้น ถ้าไม่ปรับ Order ที่ซิงค์ไม่สำเร็จและค้างที่ "แจ้งเลขติดตามแล้ว" จะไม่ถูกลองซิงค์ซ้ำ
  ส่วน guard 6 รอบเพียงพอ (รอบ 1 ตัดสต๊อก รอบ 2 เลื่อนสถานะ) และวนจบเมื่อ state ไม่เปลี่ยน
- **Alternatives considered**: แยกกฎเลื่อนสถานะเป็นฟังก์ชันนอก `runAutomation` แล้วให้หน้าจอเรียก: ละเมิด Principle I (หน้าจอไม่ควรถือกฎ)

## 3. การเดินเส้นทาง "ส่งถึง" หลังรีเซ็ต (FR-013)

- **Decision**: เพิ่มเลขติดตามที่ขนส่ง mock ตอบ `delivered` ใน `src/mock/delivery.ts` (รูปแบบเดียวกับ `failed` และ `returned`) และเพิ่ม Order ตัวอย่าง 2 รายการ
  - `ORD-24166`: "แจ้งเลขติดตามแล้ว" ตัดสต๊อกแล้ว แจ้งแล้ว ขนส่งตอบ delivered → ดึงสถานะแล้วเลื่อนเป็น "จัดส่งสำเร็จ" ทันที
  - `ORD-24165`: "อยู่ระหว่างจัดส่ง" ยังไม่แจ้งเลขติดตาม ขนส่งตอบ delivered → ต้องกดส่งเลขติดตาม แล้วระบบตัดสต๊อกและเลื่อนเป็น "จัดส่งสำเร็จ" (ทดสอบ FR-005)
  - `ORD-24174` (เดิม) ขนส่งตอบ in_transit → จบที่ "แจ้งเลขติดตามแล้ว" (ทดสอบ US1 และ SC-002)
- **Rationale**: ข้อมูลตั้งต้นเป็นวิธีที่ใช้อยู่แล้วกับ 8A ทางเลือก #2 และ #3 ผลเป็นแบบกำหนดได้ (deterministic) และไม่เพิ่มฟังก์ชันที่ไม่มี use case รองรับ
- **Alternatives considered**: เพิ่มปุ่มจำลอง "ขนส่งส่งถึง" ในหน้า /dev: ไม่จำเป็น เพราะข้อมูลตั้งต้นเดินครบทุกเส้นทางแล้ว และ DESIGN.md ห้ามเพิ่มฟังก์ชันที่ไม่มี use case

## 4. ORD-24172 (ลูกค้าปฏิเสธรับหลังตัดสต๊อก)

- **Decision**: เปลี่ยนสถานะตั้งต้นจาก "จัดส่งสำเร็จ" เป็น "แจ้งเลขติดตามแล้ว" (ยัง `stock_deducted: true`, `delivery_status: in_transit`)
- **Rationale**: เดิมเป็น "จัดส่งสำเร็จ" ทั้งที่ขนส่งตอบ returned ซึ่งขัดกับ FR-004; เมื่อดึงสถานะ ระบบเปลี่ยนเป็น "ตีกลับ/คืนสินค้า" และคืนสต๊อก (7S ทางเลือก #2) เหมือนเดิม
- ยังคง "จัดส่งสำเร็จ" ในรายการสถานะที่ `pollCarrier` เฝ้าดู เพราะตีกลับหลังส่งถึงลูกค้ายังเกิดได้ (ตาม Assumptions ใน spec)

## 5. ข้อมูลเก่าใน localStorage

- **Decision**: เปลี่ยน `STORAGE_KEY` เป็น `rsl-hub-state-v2` และ `AppState.version` เป็น 2
- **Rationale**: เบราว์เซอร์ที่เคยใช้งานเก็บ Order ที่เป็น "จัดส่งสำเร็จ" โดยขนส่งยังไม่ยืนยัน ซึ่งขัด SC-001 และจะไม่ถูกแก้เอง
  รูปร่างข้อมูลไม่เปลี่ยน แต่ข้อกำหนดของข้อมูลเปลี่ยน; ข้อมูลเป็นข้อมูลตัวอย่างจึงรีเซ็ตได้โดยไม่เสียงานจริง
- **Alternatives considered**: ปล่อยให้ผู้ใช้กดรีเซ็ตที่หน้า /dev เอง: เสี่ยงลืมแล้วทดสอบกับข้อมูลเก่า; เขียน migration แปลงสถานะ: ซับซ้อนเกินกว่าประโยชน์ของข้อมูลตัวอย่าง
- **อนุมัติแล้ว** (2026-10-12): ให้ bump เพราะระบบนี้ใช้ localStorage กับข้อมูลตัวอย่างเพื่อทดสอบ UX/UI ชั่วคราว ก่อนย้ายไปฐานข้อมูลจริง

## 6. 7A และ 10A

- **Decision**: ไม่แก้โค้ด ตรวจยืนยันตาม quickstart
- **Rationale**: `HANDED_OVER` ใน 7A มี "แจ้งเลขติดตามแล้ว" อยู่แล้ว (ได้ "รอดำเนินการพิเศษ" ตามต้องการ) `checkCancel` ปิด "จัดส่งสำเร็จ" และ "ยกเลิกแล้ว"
  `CLOSED_STATUSES` ที่ 10A ใช้มีแค่ 2 ค่านี้ ส่วน Order ที่รอขนส่งยืนยันจึงไม่ถูกลบโดยธรรมชาติ
  การคืนสต๊อกตอนตีกลับยังทำงานจากสถานะ "รอดำเนินการพิเศษ" เพราะ `pollCarrier` เฝ้าดูสถานะนั้นอยู่

## 7. หน้าจัดส่ง

- **Decision**: (ก) เพิ่ม "แจ้งเลขติดตามแล้ว" ในรายการสถานะที่ปุ่มส่งเลขติดตาม/ส่งซ้ำแสดง (ข) แสดงข้อความเล็กสีเทา "ตัดสต๊อกแล้ว" ใต้สถานะเมื่อ `stock_deducted` เป็นจริง ใช้ข้อความใหม่ใน dictionary ทั้งไทยและอังกฤษ
- **Rationale**: (ก) ถ้าไม่ทำ ปุ่มส่งซ้ำ (5S ทางเลือก #3) หายไปทันทีที่ Order จบที่ "แจ้งเลขติดตามแล้ว" (ข) FR-012 ต้องแยกสถานะ Order, สถานะขนส่ง และสถานะตัดสต๊อก/ซิงค์ให้ชัด
  ใช้ข้อความสีเทาธรรมดาเพื่อไม่แตะกฎสีสถานะใน DESIGN.md (ป้าย "รอซิงค์" เดิมใช้โทนที่มีอยู่แล้ว)
- ข้อความใหม่ "ตัดสต๊อกแล้ว" / "Stock deducted" ไม่อยู่ใน use case description ฉบับปัจจุบัน **อนุมัติแล้ว** (2026-10-12) ให้เพิ่มได้

## 8. ข้อความแจ้งเตือนเมื่อส่งถึง

- **Decision**: ไม่เพิ่ม toast สำหรับเหตุการณ์ "ส่งถึงแล้ว"
- **Rationale**: use case 8A ไม่ระบุข้อความ ("อัพเดท Order เมื่อสถานะเปลี่ยน") และ spec กำหนดไม่เพิ่มข้อความนอก use case; Admin เห็นผลจากสถานะในตาราง

## 9. ขนส่งตอบ in_transit ทับ delivered (พบจาก /speckit-analyze)

- **ปัญหา**: `trackCarrier` ตอบ `in_transit` สำหรับเลขติดตามที่ไม่อยู่ใน `MOCK_CARRIER_TRACKING` Order ที่ปิดแล้ว (`ORD-23012` เลข `4418-1001-0012`, `ORD-24168` เลข `4418-2290-0168`) มี `delivery_status: "delivered"` อยู่แล้ว
  เมื่อ `pollCarrier` ดึงสถานะครั้งแรก ค่าจะถูกเขียนทับเป็น `in_transit` ทำให้ "จัดส่งสำเร็จ" มีสถานะขนส่งไม่ตรง และ SC-001 กับ quickstart (13) ไม่ผ่าน
- **Decision**: (ก) เพิ่มรายการ `delivered` ใน `MOCK_CARRIER_TRACKING` สำหรับเลขติดตามทั้งสองนี้ (ข) ให้ `pollCarrier` ข้ามเมื่อค่าที่เก็บคือ `delivered` และขนส่งตอบ `in_transit` (ยังยอมให้เป็น `returned` หรือ `failed`)
- **Rationale**: (ก) แก้ข้อมูลตั้งต้นที่ไม่ครบ (ข) ป้องกันซ้ำเพราะพัสดุที่ส่งถึงแล้วไม่ควรกลับไปอยู่ระหว่างทาง และ Order ที่ปิดแล้วในอนาคตก็อาจไม่มีเลขใน mock
